## 完成の定義

完成は、私用の一回のツーリングを入力として、確認済みの根拠だけから日本語の
短編旅動画を一本生成し、英語表示・提出素材へ切り替えられる状態とする。

最低限の完成条件は次のすべてを満たすこと。

1. private input manifest、時計補正、映像証拠、source identityを検証してからだけ
   ローカルE2Eが実行される。
2. DirectorScriptが、根拠のあるHook / Build-up / Climax / Resolutionを持つ。
3. 欠落映像、未対応区間、却下候補を捏造せず、旅の物語として自然に扱う。
4. 無音の検証用連結ではなく、選択済みの著作権フリー音楽、字幕、地図・章表示を
   含む作品を生成する。音声ナレーションは加えない。
5. 実素材を公開・外部AI・クラウドへ送らず、公開アプリとDevpostは合成デモだけを
   用いる。
6. 英語の提出説明、3分以内のデモ動画、ライセンス・音楽情報・開発証跡を揃える。

## 実行順序

### Gate 0 — 協調開発の準備（完了）

目的: 速度を上げてもprivate素材・課金・同時編集事故を起こさない。

- Claude Codeは可視Terminalだけで実行する。`/usage`で契約内枠を人が確認できない
  場合は起動しない。`ANTHROPIC_API_KEY`を使う従量課金実行は禁止する。
- `.claude-busy` lock、明示session ID、タスク単位のpromptを使う。
- Claude CodeがCodex CLIを呼ぶ場合も、Codex CLIを別の実装者として扱う。可視Terminal、
  専用worktree、1つの限定タスク、明示した利用上限を必須とし、同じファイルを同時に
  編集しない。
- Codex CLIには実GPX、実動画、座標、ファイル名、絶対path、資格情報、private artifactを
  入力しない。Codex CLIが作った差分も、Claudeの差分・privacy・全回帰レビューを通るまで
  統合しない。
- Claudeは、Codex CLIが編集中のファイルを同時に編集しない。
- **2026-09-02の役割反転（ユーザー決定）**: Claudeが設計、コア実装、統合、privacy境界、
  全テスト、Ruff、Notion正本、commitを担当し、レビューもClaude自身が行う。Codexは
  合成fixture限定の独立小タスクを担当する。Claudeの実行は契約無料枠内に止め、
  従量課金実行は行わない。

受入条件: Claude課金は無料枠内、実素材の外部送信0、共有treeの同時書込み0。

### Gate 1 — 実素材packageの健全性確認

目的: 既存のprivate packageが同じ旅・同じ時計補正・同じsourceを参照していることを
確認し、最終E2Eに使う入力を固定する。

- private manifest、catalog、evidence review、補強snapshotの整合性をローカルだけで検証する。
- 映像のない区間と利用可能なconfirmed区間を集計し、識別子を出さないsummaryを作る。
- 条件を満たさない場合はrenderせず、原因をprivate側の次gateとして残す。

受入条件: manifest一致、時計補正確認済み、awaiting 0、少なくとも1つのconfirmed映像、
十分な合計尺。外部通信0。

担当: Claude（private実素材の読取り・入力固定・実行判断を含む）。Codexへは実素材を渡さない。

状態: **通過（2026-09-02）**。

初回判定（第20節）では、時計補正一致・awaiting 0・confirmed 1件以上を満たしたものの、
confirmed合計尺が目標尺に届かず`insufficient_confirmed_duration`で未通過だった。原因は
素材の不足ではなく、旅の欠落区間を画面に載せていなかったことにある（第21節）。Gate 2で
欠落区間を章カードとして物語に組み込み、その作品の姿を`journey-story-plan.json`として
package自身に書き出したことで、尺判定が作品尺を見られるようになった（第25節）。

再判定結果: `is_ready: true`、`blocking_reasons: []`、matched 7 / awaiting 0 / rejected 0、
confirmed 210.0秒 → **film 300.0秒 / target 300.0秒、coverage 1.0**。外部通信0。
最終E2Eの入力は固定された。

### Gate 2 — 旅の物語を完成する

目的: 「良いクリップの集合」ではなく、確認済みイベントを一本の旅として構成する。

- DirectorScriptに旅程coverage、欠落区間、Hook、Build-up、Climax、Resolutionの
  役割を明示する。
- 映像がない区間は、存在しない映像で補わず、章テキスト・地図上の移動・時間経過の
  表現候補へ変換する。
- RuleBasedDirectorを基準実装として固定し、Gemini Directorは同一contractを満たす
  任意の合成専用改善経路に留める。

受入条件: 合成fixtureとprivate-safe集計の両方で、scriptに重複event・未確認根拠・
偽の出発/到着がない。各sceneの役割と根拠が検証できる。

担当: Claudeがcontract、実装、private境界、統合、全回帰を担当する。Codexへは、
固定済みcontractに対する独立したシナリオテストまたは表示文言だけを委譲できる。

前提となる調査結果（2026-09-02）: Gate 1の尺不足は目標尺の設定ではなく、映像で裏付けられる
GPS eventの総数が上限であることに起因する。出発・到着の映像が存在せず、現状のconfirmed集合は
旅の中間だけを示す。したがってGate 2は「映像を増やす」方向では解決できず、欠落区間を
映像以外の表現へ変換する設計が本質になる。詳細は
[`current-system-handoff-ja.md`](current-system-handoff-ja.md) 第21節。

**決定済み（2026-09-02、ユーザー選択）**: 不足分は章テキスト・地図表現で埋める。目標尺の
短縮も追加素材の投入も行わない。

進捗: 欠落区間をGPS証拠だけから記述する`app/journey_gaps.py`（`JourneyGapSegment` /
`build_journey_gap_plan`）と、それをconfirmed映像と同じ時系列へ並べる
`app/story_timeline.py`（`StoryBeat` / `build_story_timeline`）を実装済み。画面上の尺は
走行時間に比例させたうえで下限3秒・上限8秒でclampする決定論的写像とした。DirectorScriptの
contractは変更せず、並行する独立contractとしてGate 3のrendererが合成する設計。

実素材での検証（ローカル読取りのみ）では、出発側の章カードで始まり到着側の章カードで
終わる完全な交互構造（footage 7、gap card 8）が得られ、作品全体の画面尺は**254.2秒**
（目標300秒）となった。Gate 1で未通過となった`insufficient_confirmed_duration`は
confirmed尺210秒から254.2秒へ縮まり、残り45.8秒は素材不足ではなくカード尺・章テキストの
配分というGate 3の調整問題であることが確定した。詳細は
[`current-system-handoff-ja.md`](current-system-handoff-ja.md) 第23節。

さらに`app/gap_chapters.py`で、欠落区間の章テキストと画面尺の配分規則を実装した。カード上の
言葉はGPS trackが証明する事実（時間・距離・標高差）だけで構成し、地名・天候・推測を載せない。
不足尺は「既に必要だったカードを長く保持する」ことだけで埋め、走行時間に比例させたうえで
上限12秒のwater-fillingで配分する。全カードを上限まで保持しても届かない場合は
`residual_shortfall_s`として報告し、目標充足を偽らない。

実素材検証の結果、**作品尺は300.0秒ちょうど、`residual_shortfall_s` = 0.0、`meets_target` =
True** となり、**Gate 1で未通過の理由とした`insufficient_confirmed_duration`は解消した**。
不足は素材の不足ではなく、旅の欠落区間を画面に載せていなかったことに起因していた。日英
どちらでも同一の尺配分・同一の区間分類となることを確認済み。詳細は
[`current-system-handoff-ja.md`](current-system-handoff-ja.md) 第24節。

最後に`app/story_package.py`で、これら3つのcontractの答えを1つの順序付き計画へ統合し、
package内に`journey-story-plan.json`として書き出せるようにした。footage beatはevent IDだけを
名指し、切り出し位置は`ride-storyteller-candidates.json`に残す（フレームの所在を1箇所にしか
書かないため）。Gate 1の尺判定はこの計画があればその作品尺を、無ければ従来の確認済み映像尺を
使い、どちらを使ったかを明示する。計画が壊れている場合は映像尺へ黙って戻らずfail closedで停止する。

**Gate 2は所期の目的を達した。** 実素材で作品尺300.0秒・beat数15（footage 7、章カード8）の
計画をpackageへ書き出し、**Gate 1が通過した**（第25節）。次はGate 3のrenderへ進む。

### Gate 3 — 作品としてのレンダー

目的: 無音の確認映像を、視聴できる短編作品へ仕上げる。

- DirectorScriptからchapter card、地図・移動表示、字幕、cut/hold等の決定論的編集指示を
  作る。
- 著作権フリー音楽はprivate local assetとしてのみ使い、曲名・作者・ライセンス情報を
  提出用に分離して記録する。音声ナレーションは追加しない。
- 音楽、字幕、映像を同一タイムラインでrenderし、欠落映像は静止の捏造ではなく
  地図・章表現へ置換する。

受入条件: 実素材を外部送信せずに、5〜10分の再生可能なローカル作品を一本生成できる。
曲の利用条件を確認でき、映像証拠gateを迂回できない。

担当: Claudeが音楽ライセンス境界、タイムラインcontract、統合、実レンダー判定を担当する。
Codexへは字幕・chapter card・FFmpeg command builderの合成fixture実装を委譲できる。

状態: **完了（2026-09-03）**。

- 章カード（`app/chapter_card.py`）: 導入済みffmpegに`drawtext`・`subtitles`が無いため
  （freetype/libass無しビルド、Homebrew現行formulaでは解決不能）、HTMLで組み
  macOS内蔵Quick Lookでラスタライズする方式を採用。新規依存ゼロ。地図表現も同経路。
- 地図: 旅全体を淡い線、当該区間を強調色で描く。経度は平均緯度の余弦で補正。図は
  正規化され、形は残り地球上の位置は残らない。**private作品内に限る**。
- 連結render（`app/story_film.py`）: 映像証拠gateを迂回できず、連結前に全segmentを
  同一フレームへ正規化する。カード描画器は差し替え可能（macOS=Quick Look、
  Linux/Cloud Run=headless Chromium）。HTMLが唯一のcontract。
- 字幕（`app/story_subtitles.py`）: SRT/WebVTTのサイドカー。焼き込まない（言語が
  encodeの属性になるため）。映像beatにはcueを付けない（何も語られていないため）。
- 統合（`app/private_journey_film.py`）: **1コマンドで作品と字幕まで完成する**。
  `python -m app.private_journey_film <package>`
- 実素材で `is_ready true` / film 300.0秒 / beat 15（footage 7・カード8）/ 字幕8cueを確認。
- **字幕と映像の一致を実素材で検証**（各cueの開始直後のフレームが正しいカードを表示し、
  cue境界の外では映像に戻ることを確認）。一致は保証されていなかったため、
  `tests/test_film_and_subtitles_agree.py`で7件の不変条件として固定した。**変異テストで
  ずれを実際に捕まえることも確認済み**（字幕側を壊すと7件中5件が失敗）。

- 音楽（`app/story_music.py`、2026-09-03）: ユーザー承認のもとCC BY 4.0の5曲を取得。
  曲の尺は作品の尺と一致しないため短ければループ・長ければトリムし、音は絵と同時に
  終わる。映像は再エンコードせずコピーする。ライセンスは成果物の一部として扱い、
  帰属文言を[`music-credits.md`](music-credits.md)へ分離記録。実素材に乗せた40秒の
  試聴を5本生成した（人は名前ではなく自分の作品に乗った音で選ぶべきであるため）。

曲は`rising-tide`（Rising Tide / Kevin MacLeod / CC BY 4.0）を採用した。曲自体が
出発から高まって落ち着く弧を描き、作品の構成と重なるため。実素材で音楽入りの作品を生成し、
mean −25.1 dB / max −3.3 dBで音が入っていることを確認済み（300.03秒、h264＋aac）。

なお実行中に2つの実バグを修正した。(1) 中断すると再生できないmp4が残っていた
（隣に書いて成功時のみ原子的に置き換える方式へ）。(2) 音楽ディレクトリのpathを推測して
おり1階層ずれていた（指定必須へ。あわせて`--music-only`で曲差し替えに再エンコード不要に）。

**作品を元素材から切り出すよう変更した（2026-09-03）。** 元素材は3840×2160/60 Mbps
なのに、作品は1280×720＝**画素数で9分の1**を出力していた。映像segmentをレビュー用
720pプロキシから取っていたためである。「人が観て確認したものがそのまま出る」という
理屈は2026-09-01の自動判定で既に失効しており、プロキシは単なる低画質の複製になっていた。
録画ファイルと窓（`FootageSource`）から直接切り出す方式へ変更し、作品を1080p、カードの
ラスタライズを1920正方形へ引き上げた。

**Gate 3は完了した。**

### 前提の変更 — 本番はクラウド製品（2026-09-03、ユーザー回答）

「本番＝他ユーザーの走行をクラウドで処理する製品」と確定した。構成を
[`cloud-architecture-ja.md`](cloud-architecture-ja.md)に設計した。

要点: **難所は計算ではなく転送**。実測で元動画68.1 GiBのうち作品に映るのは219 MiB
（0.31%）。既存パイプラインは「どの30秒を使うかはGPXとメタデータだけで決まる」順序を
既に持つため、**エッジで絞りクラウドで組む**分割がそのまま成立し、元動画は端末から
出ない。移植の障害は調査時点でQuick Look 1件のみで、既に差し替え済み・検証済み。

提出時点（2026-09-10）の範囲は「ローカル完結の実装＋合成クラウドデモ＋設計書」とし、
実素材をクラウドへ送る経路は作らない。走行映像には第三者の顔・ナンバープレートが
写るため、同意・保持ポリシーが未定のまま外部へ送ることはできない。

### 設計の是正（2026-09-03、ユーザーとの再確認）

**核心を取り違えていた。** 製品の核心は「**Geminiが実素材を判定して5分の映像を作り出す**」
ことであり、「実素材を外部へ出さない」は**開発中のゲート**にすぎなかった。私はこれを製品の
性質として固定し、提出文書にも長所として記述していた。誤りである。

さらに、私が作った作品パイプライン（`private_journey_film` → `story_package` →
`story_timeline` → `story_film`）は**Geminiを一度も参照しない**。`VideoAnalysis`を消費するのは
`story_agent.py`と`orchestrator.py`だけで、**エージェントを通すのではなく迂回**していた。

ユーザーとの確認で決まった方針:

| 論点 | 決定 |
|---|---|
| 採用区間 | **増やす**。ローカルのゲートが厳しすぎた |
| Geminiが観る対象 | 時刻照合で残った候補（約200本）。設計は未着手 |
| ローカル指標の役割 | **Geminiへ渡す前の絞り込み**として残す |
| 作品の尺 | **素材次第。5分くらい**（目標尺への水増しは廃止済み） |
| ホスト済みアプリ | **実素材を受け付ける** |
| プロキシ動画 | **LRVに依存しない。ローカルでffmpegが低解像度を生成する** |

役割の反転が要点: **ローカル＝再現率（落としすぎない）／Gemini＝適合率（選ぶ）**。
従来はローカル指標が両方を担い、どちらも中途半端だった。

実績値では 2,385窓 → 202候補 → **21本**まで絞っていた。この最後の絞り込みが誤りで、
202でGeminiへ渡す。

**着手済み**: 目標尺への水増しを廃止（第41節）。実素材で作品は300.0秒の水増しから
**254.2秒（素材どおり）**になり、Gate 1は尺でブロックしなくなった。

**決定済み（2026-09-03）**: 画質は**2段**（判定用の低解像度→採用分だけ最終画質）、
費用上限は**¥500**。

**費用見積もり（`app/analysis_budget.py`）**: 公式のメディア・トークン化に基づき、候補202本で
**¥13.2**（上限¥500）。一段で全202本を動画解析しても¥29.8。**¥500は全く厳しくない。**

なお段を素直に増やすと**逆に高くなる**ことが分かった。出力トークンが入力の約8倍の単価であり、
選別段が本解析と同じ出力を返すと、入力を削っても出力で損をする。選別段は「スコアと採否」
だけを返す設計とし、これで¥13.2（一段のみ比56%減）。予算は請求書ではなく**送信前の見積もり**で
強制し、超える場合は高い段の**手前**を締める（段自身のkeep_ratioを絞ってもその段の費用は
下がらないため）。最も締めても収まらなければ実行しない。

**着手済み（2026-09-03）**: プロキシ動画が無い素材で解析できない不具合を修正（第44節）。
フォールバック自体は実装済みだったが、入口の既定解析器がLRV以外を拒否する版で、
**フォールバックを無効化していた**。

**着手済み（2026-09-03）**: アップロード用素材のローカル生成（`app/analysis_proxy.py`、第45節）。
**プロキシ動画を前提にせず**、元ファイルから作る。Geminiが毎秒1枚で標本化することに合わせて
1 fpsで符号化し、短辺480px、音声なし。実測で**4K 12秒 → 517 KB**、stills 3枚 → 185 KB。
カスケード全体で**68.1 GiB → 74 MB（942分の1）**。

**着手済み（2026-09-03）**: 判定を採否へ繋ぐcontract（`app/gemini_selection.py`、第46節）。
**これが製品に欠けていた接合部**である。2つのスコアは別の問いに答えるため物語側を重くし
（重みは引数）、confidenceは平均に混ぜず低ければ除外し（曖昧な判定は否定ではなく判定の不在）、
採用は間隔を空け（良い1分から5本採ればその1分の作品になる）、尺は目標であって割り当てでは
ない。全候補に固定reason codeが付き、報告はモデルの文章を一切引用しない。

**着手済み（2026-09-03）**: 判定の保存と作品への配線（`app/analysis_record.py`、第47節）。
判定があればそれが「どのconfirmedクリップを使うか」を決める。記録が無ければ従来どおり全部使い、
**記録が読めない場合は停止する**（黙って従来動作へ落ちると、判定に金を払った作品とは別の作品が
切られ、それに誰も気づかない）。

**着手済み（2026-09-03）**: 送信と判定の実行部（`app/analysis_run.py`、第48節）。
`plan_analysis_run`が副作用ゼロで「何を送りいくらかかるか」を報告し、`run_analysis`は
アップローダと解析器を引数で渡さないと動かない（既定値なし、Googleへ到達しうるimportなし）。

実素材のdry runで**設計の誤りを発見・修正**した。7本の候補が1本まで絞られていた。原因は
**カスケード（予算に収める機構）がクリップの選定（品質の機構）を横取りしていた**こと。
既定を「全部通す」に変え、予算が制約になったときだけ締めるようにした。

**未決**: 初回のアップロードと初回の課金Gemini呼び出しの承認のみ。それ以外はすべて実装済み。
**判定が手に入った瞬間に作品が変わる状態。**

**着手済み（2026-09-03）**: 「採用区間を増やす」。ただし**当初の想定は測って外れた**
（第49節）。目標尺の上限は制約ではなく、上限を外しても候補は7本のまま——**24個のGPS
イベントのうち映像があるのが7個しかない**ためである。

さらに測ると、**カメラは2.3時間（走行の55%）回っていた**のに、システムが候補にしていたのは
7×30秒＝3.5分だけだった。GPSイベントは「旅のどこで何かが起きたか」に答え、録画は
「どこでカメラが回っていたか」に答える。**この2つは想定よりはるかに重ならない。**

対処として`app/footage_candidates.py`を実装し、候補を**映像そのもの**から引くようにした。

| | |
|---|---|
| 従来の候補 | **7**（GPSイベント∩映像） |
| 映像から引いた候補 | **173** |
| 判定費用 | **¥27.9**（上限¥500） |
| 送信量 | 121 MB |

**配線完了（2026-09-03、第50節）**: 判定側は映像の窓を対象にし、作品側は判定がある場合
その集合を**絞り込むのではなく置き換える**（判定は「GPSイベントが偶然入っていたクリップ」より
広い集合についてのものだから）。レンダーの素材解決も同じ出所にした。

**経路全体を通した（2026-09-03、第51節）**: Geminiの位置にstubを置き、列挙→判定→計画→
作品を通した。**配線のバグが1件見つかり修正した**——判定済みpackageでも candidate export を
無条件に読んでおり、**映像の窓だけから組んだpackage（クラウド経路がまさにそれ）では
落ちる**状態だった。単体テストは常に完全なpackageを用意していたため見えなかった。

`run_analysis`が候補ごとに縮小コピーを作り、そのファイルをアップローダへ渡すよう
繋いだ（`upload: (Path, AnalysisCandidate) -> str`）。縮小はローカルで無料なので既定を

   751→412窓（いずれも**45%減**）、採用はどちらも両stride で25窓・300秒（**尺目標は
   一切削れない**）、採用窓の重なりはbridge-e2e-v1 19/25（76%）・day-2-v1 19/19
   （baseの25窓中候補として残った19窓が**全て**そのまま選ばれた）。**質は落ちない
   ことを確認して完了**。`DEFAULT_STRIDE_S`自体を60へ変える配線（実運用の既定にする
   判断）は別途オーナー確認後に回す
4. **7.4 ローカルの無料スクリーニング**（**測って否定 2026-09-04**）: 2 ride で2つの無料信号を
   全窓に当てた。フレーム差分（1fps proxy の隣接フレーム差）は**ほぼ何も分けない**——
   カメラが乗り手に付いているので信号待ちでも画面全体が動く。採用窓を割らない閾値では
   173窓中3本・92窓中1本（2%未満）。GPS速度は 13/173・10/92（7〜11%）落とすが、
   **どの閾値でも作品が採用した窓を落とす**（20本中2本・3本、うち1本はその日の最高点 0.80）。
   停車ごとに1本だけ買う規則でも 3% で、なお1本失う。**止まっている＝映すものが無い、ではない**
   （給油・分岐・到着を作品は使っている）。作品を傷つけない最大の節約は約2%＝¥0.5/走行。
   `app/analysis_screening.py` は**測って報告するだけで、何も落とさない**
   （`python -m app.analysis_cli screen <package>`、無料）。渋滞に1時間座る ride では
   答えが変わり得るので、測定は再現可能なまま残す
5. **7.5 Flash-Lite の試験**: 順位付けの品質が Flash と一致するか（同じ40窓で順位の一致率）
6. **7.6 多利用者化**（**着手・第一片を閉じた 2026-09-08、handoff §187**）: 認証、
   利用者ごとのバケット prefix と署名付きURL、越境参照の禁止、同意・保持期間・削除
   （cloud-architecture-ja §5）。**閉じた分**: `app/tenancy.py`——prefix は利用者から
   導出（`u/<sha256先頭32桁>`。利用者自身は名前に現れない）、比較はパスの区切り単位、
   `..`・空segment・`\` は解決せず拒否、拒否文は対象を復唱しない。`judge_with` /
   `rank_with` / `upload_to_bucket` と CLI `--account` に配線（無指定なら単独利用者の
   経路は無変更）。実素材2 ride の全候補（187 + 753 = 940窓）で**越境0**、
   現在の prefix 無しの名前は**どの利用者からも受理されない**（多利用者化時に既存
   オブジェクトの移設が要る）。外部送信なし・支出¥0。
   **保持期間と削除も閉じた 2026-09-08、handoff §188**: `app/retention.py`——削除は
   prefix を単位に行い名前の一覧では行わない（どの package も覚えていない orphan こそ
   残してはいけない）、一覧が返した名前は削除前に再検査する（訊いたことは証拠ではない）、
   prefix の外を答えた一覧は sweep を止める。既定30日・上限365日、期限ちょうどは「遅い」側。
   `forget_account` は保持期間0の sweep **ではない**（未来時刻のオブジェクトが全消去を
   生き延びるため、年齢を訊かない別経路）。CLI `analysis_cli retention`
   （`--i-approve-deletion` が無ければ一覧して判断して止まる、package 引数を取らない）。
   実素材2 ride 938窓で forget は利用者の物に100%・他人の物に0%届き、
   **現在の prefix 無しの名前にはどちらも0%**——届かない保持期間の約束は約束ではないので、
   既存オブジェクトの移設は多利用者化の前提条件である。外部送信なし・実削除なし・支出¥0。
   **既存オブジェクトの移設も閉じた 2026-09-09、handoff §195**: `app/tenant_migration.py`
   ——行き先は元の名前の前に利用者 prefix を置くだけの導出（描き換えではないので二つの
   objectが一つの名前に落ちることがなく、呼び手が他人の空間を指せない）、**複製→確認→
   削除の順**（途中で落ちたら重複が残る。逆順なら穴が残る。払うのは請求書か他人の
   ride かという選択）、既に利用者空間にある object は数えて素通り（再開途中のバケットは
   正常な状態）、ただし tenant root の下で**どの利用者のものでもない** object は計画ごと
   停止（この codebase が作れない状態で、当てずっぽうが唯一取り返しのつかない誤り）。
   CLI `analysis_cli migrate`（`--i-approve-migration` が無ければ一覧して判断して止まる、
   package 引数も `--prefix` も取らない）。実素材2 ride 940窓で**移設前は forget も
   期限 sweep も 0/940 にしか届かず、移設後は 940/940**、他人の prefix には 0、
   object 数は増減なし（重複なし）、2度目の実行は 0件（冪等）。外部送信なし・支出¥0。
   **署名付きURLも閉じた 2026-09-09、handoff §196**: `app/signed_links.py`——署名付きURLは
   bearer capability なので、問いは**署名が存在する前に**答える: (1) `require_own_object`
   を署名の前に（保存された URI は所有の証拠ではなく、検査せずに署名を被せることは
   その非・証拠をアクセスに変える）、(2) **リンクは object より長生きしない**——寿命は
   「自分の上限」と「保持期間の残り」の短い方、期限に達した object は発行せず拒否
   （既定300秒・上限900秒。URLは log・履歴・screenshot に複製され、そこでは capability
   だと見えないので上限は日ではなく分）、(3) **読みだけ**——既定を持つのではなく method
   引数を取らない。拒否文は対象を復唱しない。**CLI は作らない**（出力が動く capability
   である端末コマンドは、上の危険が prompt を着ただけ）。実素材2 ride 941窓で、
   期限を越えて有効なリンクは**0本**、他人から届くリンクは**0/941**（しかも署名呼び出しが
   1回も起きない＝検査が署名の前にある）、期限4分前の走行はリンクが240秒へ短縮され、
   期限ちょうど以降は全窓が拒否。外部送信なし・支出¥0。
   **バケット側ライフサイクル規則との二重化も閉じた 2026-09-09、handoff §199**:
   `app/bucket_lifecycle.py`——`app.retention`が呼ばれて初めて削除する脆さに対する
   二つ目の鍵。設定は書かず、`app.retention.MAX_RETENTION_DAYS`（口座ごとの既定ではなく
   全口座共通の上限）から期待する規則を生成し、バケットが実際に持つ規則と読み比べる
   だけ。scope は `app.tenancy.TENANT_ROOT`（`u/`）。CLI `analysis_cli lifecycle-check
   --bucket <name>`——承認フラグは無い（何も変更しないため）。テストは模造の生dictのみ、
   実バケット・実素材には触れていない・支出¥0。
   **残り**: 認証そのもの（同意表示は 2026-09-09 に閉じた: `app/data_handling_disclosure.py`、handoff §203）
