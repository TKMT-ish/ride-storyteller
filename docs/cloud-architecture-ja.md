# Ride Storyteller クラウド構成（設計）

作成日: 2026-09-03

本書は「本番＝他の利用者のツーリングをクラウドで処理する製品」という前提での構成を定める。
実測値はすべて開発機の実素材（1回のツーリング）から取った。推定値には**推定**と明記する。

## 1. 結論を先に

**難所は計算ではなく転送である。** そして転送量は、既存パイプラインの処理順を変えずに
エッジとクラウドへ割り当てるだけで、実測 **318分の1** になる。

したがって構成は「全部クラウドへ上げる」でも「全部ローカルでやる」でもなく、
**エッジで絞り、クラウドで組む**。

## 2. 実測：どこにデータ量があるか

1回のツーリング（実素材）を段階ごとに測った値。

| 段階 | 実測 | 備考 |
|---|---|---|
| 元動画（MP4・全解像度） | **68.1 GiB** | 49ファイル |
| LRVプロキシ | **1.9 GiB** | 35ファイル。GoProが自動生成。元の約36分の1 |
| GPX | **2.56 MiB** | 7,098点 |
| 採用クリップ（7本×30秒・720p） | **219 MiB** | 作品に実際に映る全映像 |
| 物語計画（JSON） | **3.3 KiB** | 作品の構成そのもの |
| 章カード（HTML＋PNG 8枚） | **604 KiB** | |
| 完成作品（300秒・720p30） | **249.5 MiB** | 旧経路 |
| **判定用の縮小コピー（173窓×12秒・480p・1fps・無音）** | **95.0 MB** | 判定経路（2026-09-03 実測）。元の**約720分の1** |
| 完成作品（320.8秒・1080p） | **774 MB** | 判定経路 |

**68.1 GiB のうち、外へ出るのは判定用コピー 95 MB（0.13%）である。** 作品そのものは
端末で作られ、出ない。

家庭用回線の上り 30Mbps と仮定すると、68.1 GiB は**約5時間**（推定）、219 MiB は
**約1分**（推定）。モバイル回線では前者は事実上不可能。ここが設計を決める。

## 3. なぜ既存の処理順のままで足りるのか

現行パイプラインは、意図せずこの分割に適した順序をすでに持っている。

```
GPX解析 → イベント検出 → 映像との時刻照合 → 候補区間の確定 → クリップ抽出
   2.56 MiB          （メタデータのみ）              ここで初めて画素を触る
```

**「どの30秒を使うか」の判断は、GPXと動画のメタデータだけで完結する。**
画素が必要になるのは、決まった区間を切り出すときと、ハイライト検出で映像特徴を
見るときだけであり、後者はLRVプロキシ（1.9 GiB、ローカル）で足りる。

## 4. 段の分担

**2026-09-03 に実装され、実素材で一度動いた分担**（`/private-journey` の操作卓）。

### エッジ（利用者の端末のローカル console）

- 取り込み: GPX と動画フォルダ（端末内の取り込みフォルダ配下のみ）
- 動画カタログ化、GPX解析
- カメラ時計とGPS時計のズレの**提案**と確認（**利用者への確認は、ここ1点のみ**。
  提案された数字を返さないと確定できない）
- **映像の窓の列挙**（GPSイベントに限らない。実rideで173窓）
- **窓ごとの縮小コピー**（1fps・480p・無音。数百KB/窓）
- **支出の門**: 送信量と費用を表示し、その金額を円の小数2桁まで入力させてから送る
- 判定を受け取ったあとの選別・物語計画・章カード・レンダー・字幕・音楽（現状すべて端末）

エッジから外へ出るもの: **縮小コピーだけ**（実測 95 MB）。GPX も元動画も出ない。
**元動画 68.1 GiB は端末から出ない。** 出る先は利用者専用の非公開バケット、
オブジェクト名は窓のハッシュ（ファイル名・撮影時刻を含まない）。

### クラウド

- 非公開 GCS バケット（`public_access_prevention = enforced`）
- **Gemini 2.5 Flash による窓ごとの構造化判定**（Vertex AI）。実rideで173窓・¥25.6・
  約100分（逐次）。判定は端末側の記録に書き戻され、再実行は買い直さない
- （将来）物語計画〜レンダーの Cloud Run Job 化。現状は端末で完結しており、
  移す必然性は転送量からは生じない（作品 774 MB を上げるより端末で作る方が軽い）

クラウドが受け取る映像は、**判定のための縮小コピーだけ**である。作品に映る映像は
端末にしか無い。これは転送量の都合であると同時に、プライバシー上の性質でもある。

### hosted web app（公開デモ）

合成データのみ。実素材の経路（上記）はローカル console からしか通らない。

## 5. 多利用者化で新たに必要になるもの

現行は単一利用者・ローカル前提で作られている。製品化で追加が要るのは次の通り。

### 実装

- 認証と利用者ごとの分離（GCSのプレフィックス分離、署名付きURL、越境参照の禁止）
- **Cloud Run Job**でのレンダー。Serviceのリクエスト応答には収まらない
  （300秒の作品でエンコードに数分。実測で249.5 MiBを出力）
- コンテナへの追加: `ffmpeg`、`chromium`、**CJKフォント（Noto Sans CJK JP）**
- 時計補正確認のUI（現在はCLI引数）
- 進捗と失敗の可視化（Jobは非同期のため）

**CJKフォントは見落とすと危険な項目である。** 無い場合でもレイアウトは正しく描画され、
日本語の文字だけが豆腐（□）になる。エラーにならず、目視でしか気づけない。

### 方針・法務

- **同意と保持ポリシー**。走行映像には他人の顔・ナンバープレート・住居が写る。
  利用者本人だけでなく第三者の個人情報を含むため、保持期間・削除手段・
  第三者提供の有無を明示する必要がある。
- 生成物の権利（音楽ライセンスの帰属表示は作品側に埋め込む必要があるか）
- 費用モデル（1作品あたりのエンコード時間とストレージ）

## 6. 移植の障害はすでに無い

現行コードのうちクラウドへ持って行けない部分は、調査時点で **1つだけ**だった。

| 項目 | 状態 |
|---|---|
| 全contract（欠落区間・時系列・章テキスト・計画・字幕・音楽） | JSON上の純関数。環境依存なし |
| 外部プロセス実行（ffmpeg、カード描画） | すべて注入式（`runner`）。差し替え可能 |
| 章カードの描画 | **macOS専用のQuick Lookに依存していた** → 差し替え可能にし、Linux用の
headless Chromium実装を追加・実素材で検証済み |
| Gate 1健全性検証 | packageのJSONのみを読む。ファイルシステム以外に依存しない |

Quick LookとChromiumの一致は実測で確認した。**レイアウト・寸法・内容は完全に一致**し、
差はグリフのラスタライズのみ（Quick Lookの方が濃い。PSNR 25 dB、差分はすべて文字の
輪郭に集中）。同じカードだが同じ画素ではない。

## 7. ハッカソン提出時点の範囲（2026-09-10 06:00 JST）

多利用者クラウド製品の実装は、残り日数では完成しない。提出時点の範囲は次とする。

- **提出する実装**: ローカル console からの取り込み→縮小コピー→支出の門→
  **Gemini判定（実素材・実施済み）**→作品生成（Gate 1〜4、完成済み）
- **提出するクラウド実証**: 実素材の判定（1 ride、173窓、¥25.6）と、合成データのみの
  ADK / Agent Engine デモ
- **提出する設計**: 本書。実測値に基づく分割の根拠と、実装済み部分がその裏付けとなる

実素材をクラウドへ送る経路は、**開発者自身の走行**について、**承認のもとで一度**通した
（2026-09-03）。出たのは縮小コピー 95 MB のみ。多利用者化——他人の走行を預かること——は
上記5節の同意・保持ポリシーが決まるまで行わない。
